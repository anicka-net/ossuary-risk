## Summary

Ossuary detects governance risk — structural conditions in a project's maintenance that make it vulnerable to supply chain attack. It does not detect all supply chain attacks, only those where governance signals were observable before the incident.

The validation uses a **scoped evaluation framework** (Scope B) that counts only in-scope incidents toward recall. Out-of-scope incidents (credential theft on healthy projects, CI/CD exploits) are included in the dataset to validate the detection boundary, but are not penalized as false negatives.

|--------|-------------|-------------------|
| **Accuracy** | 83.7% | 92.6% |
| **Precision** | 94.7% | 94.1% |
| **Recall** | 56.2% | 76.2% |
| **F1 Score** | 0.706 | 0.842 |
| **False Positives** | 2 (jsonwebtoken, Newtonsoft.Json) | 2 (jsonwebtoken, Newtonsoft.Json) |

Numbers are reproduced from `validation_results.json` (regenerated by
`scripts/validate.py`); the methodology contracts (version, frustration

## Scoped Validation Framework

### Why scoped metrics

Reporting a single recall number across all incident types conflates fundamentally different attack classes. A tool that detected every credential theft would need to flag every package (since any maintainer can be phished), producing unacceptable false positive rates. Scoped metrics separate what the tool *claims to detect* from what it *acknowledges it cannot detect*.

### Tier definitions

An incident is **in-scope** if governance weakness was observable from public data before the attack:

| Tier | Label | In-scope? | Rule |
|------|-------|-----------|------|
| T1 | Governance decay → compromise | Yes | Governance weakness was the enabling condition |
| T2 | Protestware / sabotage | Yes | Bus factor 1 enabled unilateral action |
| T3 | Account compromise + weak governance | Yes | Credential attack, but governance weakness also present |
| T4 | Account compromise + strong governance | No | Credential attack on healthy project |
| T5 | CI/CD pipeline exploit | No | Different attack surface entirely |
| T_risk | Governance risk, no incident (yet) | Yes | Validates risk identification before incidents occur |

### Decision procedure for borderline cases

For each incident: (1) Would Ossuary's signals have shown elevated risk before the attack? (2) Was the governance weakness the enabling condition or merely coincidental? If both yes → in-scope.

The sidekiq false positive has shown up across multiple runs in
different ways. In the March 6 run it scored 60 HIGH (FP) after

`sidekiq` in the curated RubyGems list. mperham now matches the
flagship-package signal (+15) and crosses the TIER_2 threshold
(+30 ⇒ -10 risk reduction), so sidekiq lands at score 50 (MODERATE,
TN) in the v6.1 run — no longer a false positive. The underlying
governance signal (high concentration, single dominant maintainer)
is unchanged; reputation is now correctly recognised as a mitigating
factor in this ecosystem.

## Score Stability

### The problem (pre-v3.1)

Comparing two validation runs one week apart (March 6 vs March 13, hard 12-month cutoff):

- 95% of scores stable (149/157 common packages)
- 8 packages changed by ±10-20 points
- sidekiq crossed the threshold (40→60), creating a phantom false positive

Root cause: the hard 12-month cutoff for concentration. A single commit crossing the 365-day boundary shifts concentration by 2-3%, which amplifies into ±20 point score changes.

### The fix (v3.1): tapered concentration

Activity count keeps the hard 12-month cutoff (the activity modifier uses coarse buckets >50/≥12/≥4/<4 that are insensitive to boundary noise). Concentration uses a tapered window:

- 0-10 months: weight 1.0 (fully recent)
- 10-14 months: weight fades linearly from 1.0 → 0.0
- 14+ months: weight 0.0 (excluded)

A commit at month 11 doesn't vanish when it ages to month 13 — it gradually fades. This eliminates the cliff edge that caused phantom threshold crossings.

### Result

Compared to the hard-cutoff run on the same data:
- 6 scores changed (vs 8 unstable in the hard-cutoff comparison)
- sidekiq: 60→40 (FP eliminated)
- No TPs lost
- Precision: 92.3%→96.0%

The taper is not artificial smoothing — a commit from 11 months ago genuinely shouldn't have the same weight as one from last month. The hard cutoff was the artifact.

### Bus factor (v3.2): CHAOSS-aligned contributor diversity

Top-1 concentration can be misleading. A project like trivy (18% top-1) looks
distributed, but only 3 people account for 50% of commits (bus factor = 3).
v3.2 adds the CHAOSS bus factor metric alongside concentration, using the
worse signal as base risk floor:

| Bus factor | Base risk floor | Interpretation |
|-----------|----------------|----------------|
| 1 | 60 | Single person dominates (concentration already captures this) |
| 2 | 40 | Two people control the project |
| 3–5 | 40 | Small group, moderate risk |
| 6+ | 20 | Well-distributed |

Bus factor only raises the floor — it never lowers base risk below what
concentration gives. A/B testing confirmed **zero impact on Scope B
classifications** (all affected packages are controls, not incidents).

### Historical reputation reconstruction (v3.2, tightened in v6.4.2)

Historical scoring (T-1 analysis) previously stripped all current-state
metadata. v3.2 reconstructs what is verifiable at the cutoff date:

| Signal | Reconstruction method |
|--------|----------------------|
| Tenure | Compute account age at cutoff (immutable) |
| Portfolio | Filter repos by `created_at` ≤ cutoff |
| Stars | Sum from repos that existed at cutoff (conservative) |
| Org membership | Pass through (stable for recognized foundations) |
| Sponsors | Cannot reconstruct — set to 0 |

That table records the v3.2 design and its then-measured `is-promise` 70→45
change. The August audit found that repo star totals, organization membership,
and profile identity were still current observations rather than fully
historical data. Active v6.4.2 therefore uses the stricter contract:

| Signal | v6.4.2 historical treatment |
|--------|------------------------------|
| Git commits | Require both author and committer timestamps ≤ cutoff |
| Account tenure | Compute at the cutoff only when the profile is proven to match the cutoff contributor |
| Portfolio / stars / org membership / top-package list | Present-day observations; neutralized |
| Rolling downloads / repository stars | Unavailable; neutralized |
| Merge-author diversity | Unavailable from the bounded current sample; neutralized |
| Sponsors / issue sentiment / CII badge | Unavailable current snapshots; neutralized |
| Organization ownership | Retained only as an explicit stable-property proxy, not described as observed T−1 data |

Under this contract `is-promise` scores 65: current downloads no longer supply
−20, and an unproven profile binding no longer supplies −10 reputation.

### June 2026 pipeline-integrity revalidation

A full-repository review (June 2026) found and fixed several
data-collection bugs that had fed partially wrong inputs into the
May 2026 run: previously cloned repos served git history frozen at
first-clone time (fetch without fast-forward), the merge-author
sample was drawn from the *oldest* 100 merged PRs instead of the most
recent, the organization signal counted whatever the members endpoint
returned for the caller's token, and merge signals leaked present-day
data into T-1 cutoffs. After the fixes, every snapshot was invalidated
(collector version bump) and the full dataset (n=177 at that point) was
re-collected and re-scored from scratch.

**Result: the Scope B confusion matrix reproduced exactly** (at the
n=177 state then current: TP=28, FP=2, TN=118, FN=8 — same packages,
same FP/FN lists; the current n=184 matrix above adds the June Hades
holdout increment on top of this reproduced base), which is
evidence the headline claims do not rest on collection artifacts. The
unscoped view improved by one detection: `aquasecurity/trivy-action`
(T5) rose 45 → 80 because the attacker's force-pushed tag rewrite is
itself visible in the now-current git history — detection after the
fact, hence reported as a bonus, not counted in scope. Two other
out-of-scope scores shifted with fresher data (eslint-config-prettier
55 → 45, num2words 0 → 20).

### August 2026 final-cutoff revalidation

The thesis validation cutoff is **2026-08-15**. Current-state controls and
undated T_risk cases are observed at that checkpoint; dated incidents keep
their recorded day-before-incident cutoffs. A named `YYYY-MM-DD` cutoff is
inclusive through the end of that UTC day; this avoids silently excluding
commits made later on the named date. Methodology v6.4.2 closes the
remaining historical/current-state leaks and the collector was invalidated
again (`COLLECTOR_VERSION = 5`) for a new 184-case collection. Versions 3 and
4 had already been written by local July audit experiments, so reusing either
would not have invalidated the local database:

- a historical commit must have both author and committer timestamps at or
  before the cutoff, preventing later cherry-picks/rebases from appearing in
  the past;
- rolling current registry downloads and the bounded current merge-author
  sample are neutralized in historical scoring rather than backfilled;
- maintainer reputation is used historically only when collection proved that
  the GitHub profile belongs to the relevant Git contributor; bot and
  non-`User` profiles cannot receive human reputation;
- partial issue-comment failures are provisional, essential/provisional rows
  cannot enter metrics, and an incomplete run cannot overwrite the canonical
  artifact;
- transient registry failures are not persisted as permanent negative-cache
  results.

The strict run contains 184/184 evaluated rows, zero errors, zero provisional
rows, and one explicit pinned-evidence case. The original
`monarch-initiative/pyphetools` repository disappeared after the June Hades
incident, so validation uses its last observed original-repository snapshot
(collected 2026-06-10) for the fixed 2026-06-07 T−1 score. The fixture records
its provenance; a public post-incident archive independently matches 517 of
the 533 captured commit hashes and contains no extra hashes, but omits 16 later
commits and is not substituted as the score source.

A final publication audit found that the first export used a local-naive CEST
instant for current controls while git evidence is UTC-naive. Replaying the
same version-5 snapshots at the corrected `2026-08-15T15:49:38.364446Z`
instant changed no score, label, or confusion-matrix cell. It corrected small
tapered-concentration values in 115 current rows and 12-month commit counts in
13 rows. The same audit populated the previously inert per-row reputation
factor and made persisted score-cache rows methodology-versioned; those detail
and operational fixes do not change the benchmark metrics.

The Scope B matrix **reproduces the July aggregate exactly** (TP=31, FP=2,
TN=118, FN=11; precision 93.9%, recall 73.8%, F1 0.827), but four in-scope
members swap across the threshold. `es5-ext` 40→60 and `is-promise` 35→65
become T2 detections when current download protection (and, for `is-promise`,
an unproven profile binding) is neutralized. `moment` 85→45 becomes a T_risk

Thus the unchanged headline is a measured cancellation, not reuse of the old

Before the 1.0 freeze, v6.4.3 corrected two measurement semantics without
changing the fixed cohort or cutoff. First, the 12-month activity bucket now
excludes authors whose email or name contains GitHub's standard `[bot]`
marker. This changes six scores. `isarray` 25→40, `certifi` 20→35, and

55→85 and FN→TP:
502 of its 513 commits in the window were authored by `stainless-app[bot]`, so

recall 76.2%, F1 0.842). This is a post-validation measurement correction
evaluated on the already fixed cohort, not independent model evidence.

Second, commit frustration now counts only messages authored by the top non-`[bot]`
contributor, matching the existing issue-discussion contract. The prior code
treated every merged commit author as a maintainer. Four controls had false

This is a naming heuristic, not proof of humanity. Automation without the
`[bot]` convention still counts as activity and can become the maintainer
proxy for reputation and frustration. The current artifact contains a concrete
case: `kubernetes/kubernetes` resolves `k8s-ci-robot` as the top contributor
and counts its 7,602 commits in the activity field. Its final score remains 0,
but the limitation is material to interpretation.

## Reproducibility

Re-score the retained collector-v5 snapshots at the frozen checkpoint:

```bash
cd ossuary
.venv/bin/python scripts/validate.py \
  --replay-instant 2026-08-15T15:49:38.364446Z \
  --snapshot-collected-before 2026-08-15T18:48:00Z \
  --output validation_results.json
```

Replay mode is cache-only: it never contacts registries or GitHub, rejects
snapshots collected after the pinned upper bound, and fails if any required
snapshot is absent. Exact rescoring therefore requires the
retained August collector-v5 snapshot database; those raw blobs total roughly
716 MB and are not stored in this Git repository. The committed runner makes
the transformation reproducible when the frozen evidence is available, while
the published JSON preserves the resulting row-level scores and aggregates.
Independent reconstruction from an empty database is not possible after a
current-state checkpoint has passed; this is a data-availability limitation,
not treated as if historical state could be recollected.

For a from-scratch pipeline audit at the actual current date, use `--refresh`
and write a separate artifact. That measures a new checkpoint and must not
overwrite the 2026-08-15 thesis evidence.

The artifact contains both unscoped and Scope B metrics, per-tier
detection rates, and the methodology contracts (version, frustration
weight, sentiment-in-score, risk thresholds), validation cutoff and exact
current-state cutoff instant, collector version, and completeness counts so
derived docs stay in sync. The command
refuses to write the artifact if any row errors or remains provisional;
`--allow-incomplete` is only for explicitly diagnostic output. The console
output prints the same Scope B summary directly.

Filter by ecosystem:

```bash
.venv/bin/python scripts/validate.py --ecosystem cargo
```

## Data Completeness

### Incident population, not sample

The validation dataset is not a sample from a larger population. It was
assembled in two phases with different completeness properties:

- **2016–2024 core:** effectively a **census** of known governance-relevant
  supply chain incidents in the 8 supported ecosystems, cross-referenced
  against the curated incident catalogs below (whose coverage ends around
  2024).
- **2025–2026 cohort:** curated catalogs do not yet cover this period.
  These incidents were added through ongoing monitoring of vendor
  advisories and security research (Socket, Snyk, Endor Labs, vendor
  blogs) as the campaigns unfolded. **No completeness claim is made for
  this period.** What the accession process does guarantee is that
  additions were not selected for favourable outcomes: in-class
  compromises were added regardless of how the model was expected to
  score them — the June 2026 Hades cluster was folded in knowing three
  of its six cases would score as misses, and the out-of-scope 2026
  campaign rows (axios, @tanstack/router, pytorch-lightning,
  @redhat-cloud-services/frontend-components) were added as expected
  false negatives.

Three major incident catalogs were cross-referenced for the core:

| Catalog | Total incidents | Relevant to Ossuary |
|---------|----------------|-------------------|
| CNCF TAG-Security | ~89 | ~15 (rest are CI/CD, firmware, mobile) |
| IQT Labs / Atlantic Council | ~182 | ~20 (rest are typosquatting, mobile, proprietary) |
| Ladisa et al. SoK (IEEE S&P 2023) | 94 | ~15 (overlap with above) |

Additionally consulted: Socket.dev blog, Snyk advisories, Sonatype timeline,
Backstabber's Knife Collection (Ohm et al., 174 packages), Datadog malicious
packages dataset (19K+ packages), open-source-peace protestware list.

The catalogs overlap heavily. The total *documented* population of supply
chain compromises of **legitimate projects** (not typosquatting or malware
uploads) in npm, PyPI, Cargo, RubyGems, Packagist, NuGet, Go, and GitHub
currently stands at approximately **64 incidents**, all of which are in
the dataset: a census of the catalog-backed 2016–2024 core, plus the
2025–2026 cohort as observed through advisory monitoring (the v6.3
TeamPCP extension, the v6.4 May 2026 sweep, the June 2026 Hades
bioinformatics cluster, and the June 2026 Miasma addition — subject to

repositories and cannot be scored:

### Implications for statistical analysis

This is a **rare-event population**, not a sampling problem. Documented
supply chain compromises of legitimate packages number approximately
64 in the observable history of package ecosystems (2003–2026).
Additional collection effort cannot substantially increase n for the
catalog-backed core; the 2025–2026 cohort grows only as new incidents
occur or surface.

This explains why:
- **The existing ML comparison did not beat the hand-tuned model**: n≈64
  incidents is too few to estimate nonlinear feature interactions reliably
  (XGBoost achieved F1 0.787 vs hand-tuned 0.857 on the v6.2.1 baseline; see
  methodology §10.4). This is an observed result, not proof that no learned
  model can do better.
- **Bootstrap confidence intervals are wide**: recall 62–91% at 95% CI
  reflects the genuine uncertainty from a small population
- **Per-tier rates have limited statistical power**: T3 at 11/14 (79%) is
  encouraging but the CI is wide

The appropriate statistical framing is **exact binomial confidence intervals**
on a documented population (near-complete for the catalog-backed core),
not inference from a sample to a larger
population.
